# 货迹 · 大货物流追踪

独立运行于 Ubuntu VM 的中文网页 APP。Node.js 24，内置 SQLite，官网查询依赖 Playwright。无需前端构建，不修改现有 WIA / 到货协同数据库。

## 最新夜间官网监控（1.6）

默认每天巴黎时间22:00查询官网，新增运单自动加入计划，可暂停和手动立即检查。先阅读 [夜间监控IT部署说明](deploy/NIGHTLY-MONITOR.md)，执行 npm ci 并安装Chromium。真实官网无人值守首轮查询失败，当前仍需在VM验证连通性，不能按“已稳定自动取到轨迹”验收。后文旧版本API说明仅在 TRACKING_SOURCE=api 时适用。

## 已实现

- 账号＋密码登录，ADMIN / 物流专员 / 销售三种角色，12小时 HttpOnly 会话、同源写入校验、受保护面单附件。
- ADMIN 创建账户、停用/启用、修改姓名/角色、重设密码；账户修改立即撤销其原有会话。始终保留至少一个启用的 ADMIN。
- ADMIN 和物流专员可录入所有运单，创建时必须分配给一个启用的销售；可重新分配销售归属。销售只读自己的物流、时效、面单和提醒。账户密码散列不会返回客户端。
- 通知已读状态按账户隔离；变更销售归属后，原销售立即不能再读取该运单的轨迹、通知和面单，新销售可以读取。
- 运单运输方式：海运 / 卡航 / 空运 / 地铁，按用户原文保留选项。销售可见；旧运单升级后保持未填写，不猜测方式。
- 内部物流公司、确认重量、单价、总价、其他费用及其说明、币种、付款状态仅 ADMIN/物流专员可见。重量按 kg、最多3位小数；单价按币种/kg、最多4位；金额最多2位。支持 CNY/EUR/USD/GBP。总价由物流专员手工填写最终确认金额（包含其他费用），留空表示尚未确认；系统不再按重量、单价或附加费自动计算或改动总价，不涉及汇率转换。
- 新运单付款状态默认“未付”；列表与详情“已付”勾选框可直接切换并立即保存，不需提交整个编辑表单。仅ADMIN/物流专员可切换，也可取消勾选退回“未付”。已付状态记录标记时间和操作人，状态转换留审计记录；销售不可见且不能修改。此状态仅记录物流付款，不执行实际付款。
- 每票可上传多份发票和当时的产品 Excel，保留上传时间及原文件。产品表 XLS/XLSX 供归属销售下载；发票 PDF/JPG/PNG/XLS/XLSX 仅 ADMIN/物流专员下载。每份最多16MB。新建时可一并上传，已建单也可在详情补充。销售 API 不返回内部费用字段及发票名称/ID/数量，猜到发票下载地址也不可读取。
- 已建运单可从列表“编辑”或详情“编辑运单”修改：产品、单号、承运商、查询代码、目的地、运输方式、公司、重量、费用、批次、销售归属、备注和面单。物流专员可编辑但不能删除，销售只读；ADMIN 可编辑、删除及恢复。
- 发票/产品表可替换，分类不变，旧文件内容留在版本记录和数据目录，不提供物流专员删除入口。替换面单不选择文件时保留原件，物流专员不能清空已有面单。
- ADMIN 删除需输入对应单号确认，移入回收站并停止监控；物流专员/销售不可再查看，ADMIN 可恢复。恢复保留归属、资料、轨迹、文件，需手动重启监控。没有永久清空接口。
- 产品、单号、承运商、目的地、批次、备注；UPS 单号格式校验、同单号去重；修改产品和备注。
- JPG/PNG 面单上传后自动触发本地 OCR，无须额外点击。识别到唯一单号后自动填写单号及承运商，显示识别结果；识别失败、工具不可用或不能确定时，显示手动输入，交由物流专员填写。多个候选提示选择，不自行选第一票；可手动更正识别结果。替换已建运单的面单也自动识别，保存时遵循改号归档规则。截图中多张面单需逐张核对，不能自动判定全部包裹。
- Windows 预览优先使用系统 Windows.Media.Ocr（需已安装识别语言），不上传图片到外部服务；Ubuntu 使用 Tesseract＋ImageMagick 四方向识别。支持提取 UPS 1Z格式，以及明确带 FedEx/DHL 品牌和 tracking/waybill 提示的部分数字单号格式。模糊、遮挡和格式不匹配仍可能需要手填。
- 官网/17TRACK 查询入口；人工节点录入、JSON 导入；原始事件描述和来源持久化。
- 17TRACK V2.4 注册、获取轨迹、后台轮询、失败保留旧数据、错误可见、30分钟查询节流、逐票启用或暂停，签收后停止自动查询。
- 建单到揽收、揽收到签收、建单到签收、揽收到清关完成、派送到签收耗时；待揽收等待计时；超过3天无更新筛选。
- 站内提醒、未读/已读、批次已录入/签收数量、CSV导出。
- 两票用户面单的官网核验事件可用 `npm run demo` 导入；不是自动查询结果，不自动启用监控。

## 数据连接边界

默认已改为官网浏览器夜间任务，UPS官网与17TRACK网页读取组件已编写，任务会真实尝试查询；本机首轮无人值守请求失败，VM尚需联调。不是把“未查询”改字成“已监控”，只有拿到可验证事件才更新last_sync。API方式保留为可选 TRACKING_SOURCE=api，需要token和额度，API生产连通性仍未使用真实密钥验证。详见deploy/NIGHTLY-MONITOR.md。

官方 API 文档：https://api.17track.net/en/doc 。使用 `/track/v2.4/register` 和 `/gettrackinfo`，密钥仅由服务器读取。注册可能消耗额度，只有点击同步或启用监控才会注册；自动任务每分钟检查队列，每票至少30分钟请求一次。接口更新本身可能延迟，本系统不是秒级实时。暂未接 Webhook 或承运商直连 API。

轨迹按填写的承运商 provider 识别明确节点，头程货代的揽收不计作 UPS 揽收；只有 `PickedUp` 或明确的提取描述才计入提取。实际某些承运商仅返回普通到站扫描，此时提取时间会保持未知，需要核验后手动补录。清关无记录不等于未清关；不把运输中推断成已清关。单号识别到多个承运商时建议填写 17TRACK 承运商代码；不自动串联跨单号头程与末端。

时间必须带 UTC 偏移，存储为 UTC，界面显示 Europe/Paris。时效=实际秒数/86400，保留两位小数；缺失或顺序倒置不计算。建单和实发独立，录入系统的时间不能替代建单时间。样本第二票跨夏令时切换，计算包含该1小时。没有收货记录的整批不能据一个包裹签收推断完成。批次展示的数量仅为已录入单号，不是已知完整箱数。

当前支持多人角色隔离和 ADMIN 可恢复删除，暂不具备永久删除、库存/ERP联动、微信/邮件通知、批量运单导入、异常阈值自定义。请由可信内部人员维护；外网部署必须用 HTTPS 反向代理。登录限流按回环代理来源计算，多个用户可能共享限流；不采信外部伪造 X-Forwarded-For。

## 账户与升级

1.5上传面单改为自动识别优先，失败再手动填写。请同时升级前端和服务端。Windows新增 `scripts/windows-ocr.ps1`，服务端以PowerShell命令加载其逻辑，不调整系统执行策略；Ubuntu继续安装本地Tesseract/ImageMagick。OCR不返回面单全文，只返回候选单号。Windows原生解码及旋转参考微软文档：https://learn.microsoft.com/en-us/uwp/api/windows.graphics.imaging.bitmapdecoder.getsoftwarebitmapasync 。本机已用第一张用户面单实测正确识别 `1Z14V4W16800446871`，第二张模糊倒置照片无法可靠提取，正常转人工填写，不能宣称所有照片都可自动识别。

1.5共22项测试通过，新增UPS带空格及前缀纠错、多个候选、参考号/残缺号排除、FedEx/DHL带标签数字提取。真实图像OCR另以Windows引擎实测，Ubuntu引擎仍需VM部署后验证。

1.4升级自动添加其他费用金额/说明、付款状态、已付标记时间及操作人。已有运单默认“未付”，不会推断历史是否付款，历史总价原样保留。付款快捷接口只更新付款状态及标记信息，不触发运单轨迹重置或金额计算。费用编辑不修改付款状态，标记已付也不修改费用；留空总价不会生成金额。单价/重量/其他费用改变后由物流专员自行核对并填写最终总价。升级前按已有流程停机备份。

1.3升级会自动添加回收站字段、文件版本表和旧轨迹归档表，仍需停机备份后升级。修改运单号、承运商或承运商查询代码时，系统将当前事件、通知和原始API快照保存在 `tracking_archives`，清空当前活跃轨迹/通知并重置查询状态、暂停监控，避免旧包裹事件污染新单号时效；产品、费用、销售归属、文件保留。普通资料修改不重置轨迹。运单编辑前值记入仅存于服务器的 `audit_log`；轨迹归档和文件旧版当前不提供前端历史查看。正在同步的运单需等待同步结束后再编辑或删除。平台上旧单号的注册不会自动注销。

删除为数据库软删除，原始文件不从磁盘移除，后台同步、活跃列表、消息和销售文件读取都排除删除运单。同号在回收站中也不允许新建重复记录，ADMIN 应先恢复。回收站只对 ADMIN 开放；没有永久删除API。已删除运单的已知面单URL对ADMIN/物流专员仍属于内部附件可读范围；销售不可通过此URL查看，仅恢复后的所属销售重新可读。

1.2升级同样先停服务备份，再更新源码。启动会为旧运单添加运输方式、内部费用等字段以及文件表，不删除旧数据。`deploy/nginx.conf` 的请求体上限从12m调整为24m，以支持16MB文件的JSON上传；反向代理需同步更新。原面单仍限8MB。所有上传文件（包括发票、产品表）保存在数据目录的 `labels/`，数据库 `documents` 表记录类别和归属，现有备份脚本会一起备份。文件默认强制下载，不在线执行或渲染 Excel；系统不解析表格内容、公式或验证其中的业务金额，不修改上传原件。格式校验检查扩展名和文件头，不是完整的Office文件安全扫描。

首次启动使用 `ADMIN_PASSWORD_HASH` 初始化唯一的 `admin` 账户，显示名和角色均为 ADMIN。账号登录不区分大小写，因此可输入 `ADMIN`。登录后在“账户管理”中先创建销售及物流专员，再由物流专员新增运单并选择归属销售。员工不能自行注册或修改自己的角色。当前允许管理员重设密码，没有找回密码邮件。

初始化后账户密码以数据库为准，环境变量不会在重启时覆盖已存在账户；之后通过 ADMIN 账户管理重设密码。保管好至少一个管理员密码。账户操作以及运单创建、归属变更在本地 `audit_log` 留下记录，不含密码。

从1.0升级前先停止服务并备份数据和面单。1.1启动自动添加账户、销售归属、逐账户已读、审计等表/字段；旧运单/轨迹/附件保留，旧会话失效，需要用 `ADMIN`＋原环境管理员密码重新登录。旧运单保持“未分配销售”，仅 ADMIN/物流专员可见，进入运单详情的“修改产品、批次与备注”分配后对应销售可见。旧全局已读状态不迁移为任何账户的已读，避免某人读过导致其他人漏提醒。

销售可查看所属运单的物流、备注和面单内容，物流人员应只记录适合销售查看的信息。物流专员可以维护全部运单及销售归属，不能管理账户。已经分配运单的销售需先转移全部归属，再改为其他角色；停用销售不会删除运单，仍可由 ADMIN/物流专员重新分配。账号停用不删除数据。

## 本地启动

1. Node 24+，运行 `npm run password`，生成密码散列，保存到私有环境文件（不要发送密码到聊天）。
2. 复制 `.env.example` 到仓库外，配置 `APP_ORIGIN=http://localhost:5187`、本地绝对 `CARGO_DATA_DIR`、散列。Windows 可删去 Tesseract 路径配置或改成已安装程序的绝对路径。
3. `node --env-file=/path/to/app.env server.mjs`，打开 http://localhost:5187 。必须用和 APP_ORIGIN 一致的地址；首次用账号 `ADMIN` 和生成散列时输入的密码登录。
4. 可选：`node --env-file=/path/to/app.env scripts/seed.mjs` 导入两票已核验样本。产品名待填写，第二票仅有8件中的1件。

## Ubuntu VM 部署

参考已有系统记录，默认 Node 位于 `~/.local/opt/node/bin/node`，用户级 systemd，反向代理。请在 VM 核对实际路径，本包未连接/修改现有 VM。

1. 将此目录放到 `~/.local/opt/cargo-tracker`。执行 `npm ci`，随后按夜间监控说明安装 Chromium。
2. 如需面单 OCR，由管理员运行 `sudo apt-get install tesseract-ocr imagemagick`。未安装仍可上传、查看面单、手输单号。只接受可信 JPG/PNG；生产环境保持图像工具更新、限制 VM 资源，超时或无法识别可手动录入。
3. 创建 `~/.config/cargo-tracker` 和 `~/.local/share/cargo-tracker`，权限700。环境文件放 `~/.config/cargo-tracker/app.env`，权限600。数据目录用真实绝对路径；通过 `npm run password` 生成自己的散列，设置正式 HTTPS `APP_ORIGIN`。不要使用演示密码。
4. 复制 `deploy/cargo-tracker.service` 到 `~/.config/systemd/user/`。核对 ExecStart Node 路径后执行 `systemctl --user daemon-reload`、`systemctl --user enable --now cargo-tracker`。需要注销后继续运行时由 IT 配置该用户的 linger。
5. 在独立子域名的 HTTPS Nginx server 中加入 `deploy/nginx.conf` 内容，使用现有证书流程。服务只监听127.0.0.1:5187，不占用已有5173/8877端口。
6. `journalctl --user -u cargo-tracker -n 50` 检查日志，`curl http://127.0.0.1:5187/health` 验证进程，正式地址测试登录、上传、节点录入、通知、重启后数据保留。
7. 官网方式配置 TRACKING_SOURCE=website、MONITOR_TIMEZONE=Europe/Paris、MONITOR_HOUR=22，启动后默认加入夜间计划。手动执行首次查询并核对成功结果。若改用API，显式设置 TRACKING_SOURCE=api 和 TRACK17_TOKEN，API注册可能消耗额度。

只运行一个进程、一个实例，不支持共享网络盘和多副本。VM 关机期间不能同步。尚未部署到真实 VM，systemd/Nginx 和 Linux OCR 需实机验收。

## 备份与恢复

SQLite 位于数据目录 `cargo.sqlite`；`labels/` 为原始面单，含个人地址信息，禁止公开静态挂载。原始 API 快照、轨迹、站内消息、会话也在库中。附件上传后取消创建会留下未关联文件，可在停机备份后由管理员核查清理。

建议停止服务再执行 `node --env-file=/私有/app.env scripts/backup.mjs /新的空备份目录`，完成后启动服务；脚本使用 SQLite backup API 并复制所有面单。不要在线仅复制主库或混用旧 WAL。恢复时停止服务，将备份恢复到新的空数据目录、检查数据库完整性和面单，更新配置后启动。恢复前清空 `sessions` 表使旧会话失效。备份同样包含私密数据，设为仅管理员可读。不要将数据库或密钥混入源码 ZIP。
